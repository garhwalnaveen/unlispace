# Transfer follow-up — 26 October 2026

The original 50 MB and 1 GB measurements remain the baseline. This pass changes the
implementation; it does not replace those measurements with an unmeasured speed claim.

## Implemented

- Apple Silicon Cargo builds launched from `engine/` (or its nested `smb/` workspace)
  enable `aes_armv8`, the opt-in runtime-detected hardware path required by the pinned
  `aes` 0.8.4 library. SMB signing and encryption remain enabled and retain their existing
  algorithms and validation. Disassembly of the tested SMB executable contains ARM AES
  instructions (`aese`/`aesmc`). Intel builds are unaffected.
- VFS reads capture their local overlay bytes before releasing the journal lock and fetching
  cloud shards. Slow cloud retrieval can no longer hold that lock across its shard requests.
  The snapshot is safe if another write/truncate or publication collects the old blob while
  the network request is outstanding. Metadata cache misses still resolve under the lock.
- Reads, file lookups and directory listings with already cached metadata no longer rewrite and fsync the entire SQLite journal.
  Newly loaded metadata/manifests still persist for restart/offline recovery.
- Partial reads that verify a disk-cached shard now retain it in the existing bounded RAM LRU.
  Later small reads reuse the verified bytes instead of rereading and hashing the full shard.

## Validation

- `cd engine && cargo test -p uls-vfs -p uls-client --locked`: **77 tests passed in the initial gate** (later VFS additions bring its focused gate to 36 tests).
  New regressions exercise a delayed cloud read concurrently with local truncate/blob
  collection/write/flush, check that cached reads do not modify SQLite `data_version`, and
  evict a disk shard between partial reads to confirm verified RAM reuse without a GET.
- `cd engine/smb && CARGO_TARGET_DIR=../target cargo test -p uls-smb -p smb-server -p uls-vfs-backend --locked`:
  **all passed**, including 479 vendor unit tests, the signing/encryption and transport
  integration suites, 8 adapter wire tests, 2 bridge unit tests and 4 VFS bridge tests.
  The existing 50 MiB signed wire round trip now explicitly FLUSHes, CLOSEs, reopens and
  verifies all bytes before continuing its lock checks.
- `git diff --check` passed for the changed engine files.

## Boundary of the initial unit/protocol gate

The initial loopback gate did not exercise the kernel 1 GB failure. The later native
investigation below reproduced it and isolated its session-reconnect chain. Loopback tests
alone do not establish kernel behavior, hosted reliability or throughput. All native runs
in this follow-up use generated data, local Workers and isolated mounts/cache; the user's
hosted files, settings and permissions remain unchanged.

Rebuild the bundled SMB engine from `engine/`, then repeat the original generated-data
50 MB and 1 GB procedures with a release engine, signing intact, matched power settings,
empty benchmark shard caches, exact byte counts and SHA-256 verification. Report local
write/fsync/close, cloud publication and cold retrieval separately. Large-file publication
still uploads missing shards serially; profile its staging/commit path before choosing a
concurrency change or attributing the remaining network gap to architecture.

## Native investigation after implementation

An opt-in local integration run used the rebuilt debug SMB engine, isolated local Workers,
an ephemeral account, and a generated **1,000,000,000-byte** payload. It finished with
**41 checks passed and 12 failed**; cleanup reported all owned processes stopped and no
NFS/SMB mounts remaining. `/tmp/unlispace-e2e-stress.log` retains the complete table.
This run modified only its generated fixtures and isolated mount/cache state, not the
user's existing drives or hosted deployment. It supersedes the earlier statement above
that no kernel-mounted workload had been attempted in this pass.

The failures do not establish a new transfer-speed result:

- The initial NFS read exceeded its 30-second command limit. The initial SMB text and
  8 MiB copies exceeded their 10-second command limits. Those missing fixtures caused
  later move/delete/byte-comparison failures, so these rows are not independent bugs.
- The 1 GB native copy exceeded its **176-second** child-process deadline before a
  successful write/fsync/close result was returned. Publication and cold-remount checks
  correctly failed their prerequisite checks; neither integrity check completed.
- One new proxy-rejection assertion expected a diagnostic message, while the deliberate
  secret-scrubbing socket helper exposes only `bad_request`. That harness assertion was
  corrected separately; the API rejection itself was correct.
- Remote CLI-to-mounted-file updates, conflict preservation, journal-cap rejection,
  unmount/shutdown and all nine real M3 Worker checks passed. Offline native acceptance
  failed and remains unresolved.

do not count a later drained queue as a successful native close or full-file read. No
permission setting should be weakened to obtain a benchmark result.

### Completed 50 MB repeat

The next isolated run passed **53 checks with zero failures**, including native NFS/SMB,
offline access while the local data plane was suspended, and cleanup. The full table is
`/tmp/unlispace-e2e-50mb-final.log`.

- 50,000,000 random bytes: native write, explicit fsync and close completed in **2.65 s**;
  fsync took **2.58 s**, and close rounded to **0.00 s**.
- The journal drained and an independent CLI download matched length and SHA-256;
  that verification phase took **5 s** after native acceptance.
- After unmounting, clearing the verified isolated disk shard cache, and remounting with a
  new VFS/kernel mount, native retrieval matched length and SHA-256 in **6.01 s**.

This confirms the earlier access/timeouts were not persistent for the 50 MB local workload.
These are local Worker results using the current debug engine, not a new hosted comparison
against Space or a matched release benchmark. They do not by themselves resolve the 1 GB
case; a new 1 GB run is pending separately.

### Reproduced 1 GB close failure and scheduling diagnosis

A later isolated 1 GB debug-engine run reproduced the original failure after accepting
exactly 1,000,000,000 bytes: the worker identified **target close** as the failing phase,
returning `EBADF` after 148.73 s. This was not an input-file close or a partial-byte count.
The scrubbed SMB trace is `/tmp/unlispace-smb-diagnostic-1793035605365.log`.

- At `17:24:44.273962Z`, session 1 WRITE message 12716 began. Its successful response did
  not appear until `17:25:00.953877Z`, a **16.680 s** request stall.
- At `17:24:54.422134Z`, about 10.15 s into that wait, macOS opened another connection.
  Session setup created session 2 and removed the old session. Queued old-session WRITEs
  then received `0xC0000203` (`USER_SESSION_DELETED`); an initial WRITE using the previous
  open on session 2 received `0xC0000128` (`FILE_CLOSED`). The client reopened and retried.
- Later WRITEs had further 18–19 s gaps. Actual server CLOSE handlers all returned success
  quickly; there were no missing-open CLOSE rejections. Thus suppressing a backend CLOSE
  error would not address the observed failure.
- The active sample `/tmp/unlispace-large-close-flush-sample.txt` placed 431 of 858 samples
  in publisher folding: 329 in SHA-256 and 92 in chunk-boundary scanning. Local-file reads
  can resolve ready inside the async fold loop, allowing a large fold to occupy one Tokio
  poll without handing execution back to the socket tasks.

The implementation now yields cooperatively between completed chunks. A current-thread
fairness regression accompanies this change. This addresses the observed scheduling stall;
it is not, by itself, a claim that every native 1 GB workflow is accepted.

### Post-yield debug bounds

The post-yield trace `/tmp/unlispace-smb-diagnostic-1793036459672.log` records 1,358 completed
WRITEs. The slowest response was **5.153 s**, followed by 3.408 s; no WRITE reached the
previous 10 s reconnection interval. One connection/session remained in use until cleanup,
with no reconnect, missing-open CLOSE rejection or failing CLOSE response. Independent
local socket probes during the queued 1 GB publication returned `status` in **10 ms** and
`uploads` in **4 ms**. This supports restored daemon responsiveness during the large fold.

The debug native-copy check nevertheless **failed its unchanged 176 s command deadline**.
Its full write/fsync/close acceptance is therefore not a pass. The remaining publication
and independent CLI verification were cancelled by the coordinator while switching to an
optimized-engine run; the interrupted CLI exit and dependent unexecuted cold-read check are
excluded from product failure counts. Cleanup completed and removed the owned processes
and mounts. A release-engine result must be recorded separately; it cannot replace these
debug failures or establish a new hosted comparison against Space.


### Completed optimized 1 GB acceptance

The final uninterrupted run used `engine/target/release/ulsd`, built with
`cargo build --release -p ulsd --features smb --locked`, against isolated local Workers.
`E2E_SMB=1 E2E_STRESS_BYTES=1000000000 E2E_SMB_DIAGNOSTIC=1` enabled the native workload.
It passed **53 checks with zero failures**, including cleanup. The full sanitized table is
retained in `tests/e2e/last-run.txt`; the original run log is
`/tmp/unlispace-e2e-1gb-release-final.log` and the scrubbed SMB trace is
`/tmp/unlispace-smb-diagnostic-1793038642902.log`.

| Phase | Result |
| --- | --- |
| Native write, fsync, close | Exactly 1,000,000,000 random bytes accepted in **15.11 s**; fsync **2.82 s**, close **0.01 s** |
| Publication and independent download | Journal drained; independent length and SHA-256 matched; **140 s** after native acceptance, including both publication and verification |
| Cold remount read | Empty isolated disk shard cache and a new VFS/kernel mount; length and SHA-256 matched in **20.19 s** |
| Recovery and adjacent workflows | NFS, save/rename/delete/xattrs, remote changes, conflict preservation, offline pin reads during data-plane suspension, journal cap, S3/forks/keys/quota, shutdown and cleanup all passed |

This resolves the reproduced native 1 GB save/close failure for the tested release/local
workload. It does not erase the debug failures above or establish hosted throughput parity
with Space. The 140 s phase combines upload and independent download, so it must not be
reported as upload-only time. A matched hosted comparison and profiling serial publication
remain separate performance acceptance work.

The preceding optimized run was interrupted with the conversation before its stress result
was emitted; it is excluded from pass/fail counts. Its owned processes, mount and temporary
data were removed before this clean run. The final review app and DMG embed the tested
release daemon and pass deep signature/read-only installer checks; they use ad hoc signing
and are not notarized distribution artifacts.
