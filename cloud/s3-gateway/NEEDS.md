# Integration needs for 16-s3-gateway-m3

- **API agent:** deploy the normative M3 `ControlPlane` entrypoint on `unlispace-api`, with all §3.3 methods and coded errors. The gateway binds `CONTROL_PLANE` to that entrypoint and `API` to its default fetch handler for session `/keys` forwarding. Real credentials never use `MemoryKeyResolver` or an S3 master secret in this Worker.
- **Data-plane agent:** file/folder rename must preserve content history by node identity, including reads/restores by a pre-rename version id at the new path. Currently `drive.ts` `versions` filters `versions.path` and `manifest(versionId)` requires the old path; gateway archives bridge its own S3 renames but cannot cover renames performed by desktop/API clients. Please return content `operation` and `restoredFrom` on version rows (including in forks); otherwise native writes/restores cannot carry exact operation/provenance through S3 history.
- **Coordinator:** exercise real ControlPlane/DataPlane service bindings, real D1 key revocation and ancestor/current-role changes, quota/placement/fork operations and native-client rename/history before declaring production parity. No deployment or remote-service calls were made here.

Gateway history archives and annotations are separate S3State writes after data-plane commits; they are not an atomic cross-DO transaction. Concurrent subtree writers, process failure between commits and annotations, and large histories require the data-plane identity/history change above. A fork created outside S3 does not copy S3-only annotations. This is an integration limitation, not evidence that live cross-client parity passed.
